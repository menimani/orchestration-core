ORCHESTRATION CORE

An autonomous improvement loop
for a software repository

MIT licensed Node 23.6+ TypeScript, no build step
Nothing here decides that shipping is safe — deployment stays a human action

What it does

It scans the codebase, turns findings into tasks, runs them through an agent CLI in isolated git worktrees, merges what passes the repository's own tests, and opens the pull request.

scan → tasks → worktrees → test → merge → cycle gate → … → review → promote

A task merges only after the tests its changed paths select pass against the branch tip. Cycles end at a gate that pushes and updates a draft pull request. With AUTO_REVIEW=true an agent reads the whole branch diff, and its findings become fix tasks.

What you supply

AdapterSelectorBundled
forgeFORGEgithub, through gh
runnerRUNNERcodex
projectPROJECTnone — you write it

The project adapter names your gates, suites and risk signals. It lives outside the package, so a subtree pull never touches it.

Install

git subtree add --prefix=orchestration/ts \
  https://github.com/menimani/orchestration-core.git main --squash
npm ci --prefix orchestration/ts
node orchestration/ts/src/cli.ts init <project-name>
BEFORE YOU START A RUN Start it on a topic branch, never on your default branch. The loop commits and merges on its own. 
MAX_SCAN_CYCLES=12 MAX_PARALLEL=8 AUTO_REVIEW=true \
  node orchestration/ts/src/cli.ts loop --daemon

Settings worth knowing

ISSUE_QUEUE_ENABLEDfalseKeep the backlog in forge issues so several machines share it

Requirements

  • Node 23.6 or later — the TypeScript sources are executed natively
  • git, and Bash on Windows for the bundled Codex runner
  • An agent CLI and a forge CLI
WHY IT IS MADE OF ORDINARY PARTS git worktrees, a text queue, forge issues, and the tests the repository already had. Every behaviour in the specification was learned from a specific failure, and the suite pins it.
